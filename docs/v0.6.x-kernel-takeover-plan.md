# 《v0.6.x 内核深度接管方案》

> 目标：把 Rust 后端从"放养"Mihomo 内核，升级为对内核生命周期、日志、连接池的**强接管**。
> 前置侦察：已逐文件核对 mihomo `v1.19.30` 源码（`log/`、`hub/route/`、`tunnel/statistic/`、`constant/`），以及本项目现有 `core/sidecar.rs`、`core/ingest.rs`、`core/kernel_events.rs`、`commands/mihomo.rs`、`stores/kernel.ts`。
> 状态：**方案待确认，未写业务代码。**

---

## 0. 结论速览（TL;DR）

| 方向 | 现状 | 可行性 | 关键结论 |
|---|---|---|---|
| ① 结构化日志 | mihomo **无**原生 JSON 日志开关 | ⚠️ 部分可行，需转向 | `?format=structured` 的 `Fields` 被硬编码为空，无法"零容忍 serde_json"解析出 DNS 时延/TCP 失败；必须转向**文本 payload 防御性解析** + 从 `/connections` metadata + `/dns/query` 采集细粒度信号 |
| ② 毫秒级守护 | 检测已毫秒级，但**无后端自动重启** | ✅ 完全可行 | 崩溃检测在 `CommandEvent::Terminated`（channel 即时唤醒）；缺的是 Rust 侧自主重启 + 指数退避 + 前端防抖（防 flicker storm） |
| ③ 连接池干预 | `DELETE /connections/{id}` 与 `/connections`（全杀）**已存在且已封装** | ✅ 完全可行 | 缺的是**条件过滤层**：mihomo 只支持按 UUID 或全杀，Rust 需 GET snapshot → 按 metadata 过滤 → 逐个 DELETE |

一句话：**方向①要"拨乱反正"，方向②要把重启权从前端收回到 Rust，方向③要补一层条件匹配。**

## 2. 方向一：结构化日志（Structured Logging）

### 2.1 源码事实（已核实）

1. **默认格式是 TextFormatter，不是 JSON**。`log/log.go` 用 logrus + `TextFormatter`；`log.Event{LogLevel, Payload}` 只有 `type:string` + `payload:string` 两个字段。
2. **唯一的结构化开关**是 `/logs` WS 的 `?format=structured` 查询参数（`hub/route/server.go::getLogs`），返回 `LogStructured{Time, Level, Message, Fields:[]LogStructuredField}`。
3. **致命点**：`LogStructured.Fields` 被**硬编码为空**（`Fields: []LogStructuredField{}`）——即 mihomo 自身**从不产出**任何结构化子字段。DNS 时延、TCP 握手失败这类细粒度信息，在日志里只以**纯文本**形式出现（如 `[TCP] connected <host>`、`[DNS] ...`）。
4. **无环境变量/配置键**能打开 JSON 日志。`config/config.go` 只有 `log-level`（日志级别），没有"结构化/JSON 输出"开关。
5. `payload` 是纯文本字符串；`log-level` 可在 yaml 里控制级别（DEBUG/INFO/WARNING/ERROR/SILENT，`constant/log.go` 对应 `LogLevel`）。

### 2.2 可行性结论

> **"零容忍 serde_json 反序列化 DNS 时延 / TCP 失败"这条路在日志侧走不通。** mihomo 不暴露结构化字段，任何 JSON 反序列化都是对着一个空 `Fields` 数组空转。

**但这不等于方向①失败——它只是换了个采集源。** 细粒度信号其实躺在两个更好的地方：

1. **`/connections` 的 metadata**（`TrackerInfo.metadata` → `constant/metadata.go`）：`network`、`type`、`sourceIP`、`destinationIP`、`sourcePort`、`destinationPort`、`host`、`sniffHost`、`process`、`processPath`、`rule`、`rulePayload`、`dnsMode`、`inboundName`、`remoteDestination` —— 这些是**强类型字段**，天然可 `serde_json` 零容忍解析，比日志文本可靠得多。
2. **`GET /dns/query?name=&type=`**（`hub/route/dns.go`）：走 mihomo 自己的 resolver，Rust 可在**本侧**计时 → 拿到精确 DNS 时延，无需依赖日志。
3. **TCP 失败**：mihomo 日志里的 `[TCP]` 文本是唯一信号源，但**注意** mihomo 对每个连接的失败**不一定会输出一条独立可关联的日志**——失败信号更可靠地从 `DELETE` 后是否重连 / 节点延迟测速（`GET /proxies/{name}/delay`）异常中推断。

### 2.3 技术方案（三层降级架构）

```
Layer A（保留现状，兜底）  parse_log 继续消费 /logs 纯文本 {type,payload}
        │  文本里能稳定切出的：level + message（现 LogPayload 已够）
        ▼
Layer B（增强，新增）      对 payload 文本做"防御性"切分，抽 4 类可稳定命中的字段：
        ① [DNS] 前缀       → dns_event（query/result/耗时若文本含数字）
        ② [TCP] 前缀       → tcp_event（connected/refused/timeout + host）
        ③ rule/rulePayload → 命中规则名（正则从 payload 抽 "matched rule X"）
        ④ 节点切换          → proxy switch（"switched to X"）
        失败命中就丢弃，绝不 panic；仍以 serde 先解 RawLog 外层，再对 payload 二次解析
        ▼
Layer C（主采集源，新增） 不再依赖日志拿细粒度信号，改从控制面 REST/WS 直接采：
        ① /connections WS（?interval=）→ TrackerInfo.metadata 强类型字段（零容忍 serde）
        ② GET /dns/query → Rust 侧计时 → 精确 DNS 时延
        ③ GET /proxies/{name}/delay → 节点延迟异常 → 触发连接清理（见方向三）
```

**建议**：把 `?format=structured` 当作**过渡**方案评估是否接入（返回的 `Time/Level/Message` 字段是干净的、机器可读的，能替代一部分文本切分），但因为 `Fields` 恒空，**不要对它的子字段抱期待**。

|---|---|

## 3. 方向二：毫秒级异常守护（Supervisor with Backoff）

### 3.1 现状事实（已核实）

1. **崩溃检测已经是毫秒级**：`core/sidecar.rs` 的 drain task 里 `CommandEvent::Terminated(TerminatedPayload{code,signal})` 在 child 退出时**立即**被 channel 唤醒（`sidecar.rs:319`），据此设置 `KernelState::Stopped`（code==0）/ `KernelState::Crashed`（非 0），并 emit `KERNEL_STATE` + `KERNEL_TERMINATED`。
2. **但后端不重启**：Rust 的 `Terminated` 分支只 `break`，**不 relaunch**。`restart()` 只在用户/前端显式调用时执行（stop + 400ms sleep + start，`sidecar.rs:361`）。
3. **自动重启在前端**：`stores/kernel.ts::autoRestartOnCrash`（`kernel.ts:197`）监听 `kernel://terminated`，非 0 退出才触发，指数退避 `1s → 2s → 4s → cap 30s`。
4. **潜在问题**：
   - 重启权在前端 → **WebView 窗口关闭/重载/崩溃时，自动重启就断了**；Rust 侧本应自治。
   - `state` 是 Rust 事件单写驱动，但前端 `autoRestartOnCrash` 里 `await this.restart()` 会再走一次 `restart_kernel` IPC，与后端状态存在竞态（`_restartInFlight` 只是前端防重入，挡不住跨进程竞态）。
   - **flicker storm 风险**：端口被占/网卡重置等场景，内核可能"起了就崩、崩了就起"，`KERNEL_STATE` 高频翻转（Starting↔Crashed），前端 store 每次翻转都重渲染 → 抖动。

### 3.2 技术方案

**核心动作：把"监督者 + 退避 + 重启"整体下沉到 Rust**，前端只做"消费状态 + 展示"。

```
                     ┌─────────────────────────────────────────┐
                     │  core/supervisor.rs（新建，唯一写状态者） │
                     │                                          │
   sidecar Terminated ──► 判 code==0 ?                          │
   (channel 即时)          ├─ 0  → 用户主动停 → 不重启，emit Stopped │
                           └─ ≠0 → 崩溃 → 指数退避重启          │
                                     │                          │
                                     ├─ attempt++  backoff=min(30s, 1s*2^(n-1)) │
                                     ├─ 端口探测（GET /version 或 TCP 探活，2s） │
                                     ├─ 成功后 attempt 归零       │
                                     └─ 超限（如 5 次）→ 放弃，emit 需要人工介入 │
                     └─────────────────────────────────────────┘
```

关键设计点：

1. **状态单写**：`KernelState` 的写入收口到 supervisor 一处（现在是 drain task + `start()` + `stop()` 三处写），避免竞态。
2. **退避 + 抖动（jitter）**：`backoff = min(cap, base * 2^(n-1))`，加 ±20% 随机抖动，防止多实例同拍。
3. **端口占用/网卡重置等"起了就崩"场景**：用**连续失败计数 + 熔断**——连续 5 次仍崩则停止自动重启，`emit KernelState::Crashed` + 一条"需要人工介入"日志，等用户显式 Start 或配置变更再重置计数。
4. **前端防抖（防 flicker storm）**：前端 store 对 `KERNEL_STATE` 做 **hysteresis 滞回**——例如状态在 500ms 内高频翻转时，UI 只显示"重启中/异常"的稳定态，而不是每 100ms 重渲染一次；或后端在 supervisor 内把连续的状态抖动**合并**成一个"暂态"事件，只有稳定超过阈值才推真实终态。
5. **探活**：复用现有 `ingest.rs` 的思路——重启后先 `GET /version`（2s 超时）确认端口真的起来了，再宣告 `Running`，避免"spawn 成功但端口没绑上"就误报 Running。

### 3.3 涉及 Rust 模块

| 模块 | 改动 |
|---|---|
| `core/supervisor.rs` | **新建**：监督循环、指数退避、熔断、探活、状态单写 |
| `core/sidecar.rs` | `Terminated` 分支不再 `break` 后丢弃，改为把"退出信号"交给 supervisor；`restart()` 保持给用户手动用；`KernelState` 可能增加 `Recovering` 暂态 |
| `core/kernel_events.rs` | 新增 `SupervisorEvent`（`Recovering` / `GiveUp` / `Recovered`）事件 |
| `commands/kernel.rs` | `start_kernel`/`restart_kernel` 与 supervisor 的状态机对齐（避免与自动重启打架） |
| `stores/kernel.ts` | **删掉 `autoRestartOnCrash`**，改为消费 Rust 侧 supervisor 事件；新增状态滞回（防抖） |

## 4. 方向三：连接池细粒度干预（Connection Management）

### 4.1 现状事实（已核实）

1. **mihomo 控制面**（`hub/route/connections.go`）：
   - `GET /connections` → `Snapshot{DownloadTotal, UploadTotal, Connections[]}`（另有 WS `?interval=` 实时推）
   - `DELETE /connections/{id}` → `closeConnection`（`statistic.DefaultManager.Get(id)` + `c.Close()`）
   - `DELETE /connections`（根路径）→ `closeAllConnections`（Range 所有 tracker 全 Close）
2. **无"按条件删除"端点**——mihomo 只认**精确 UUID** 或**全杀**。
3. **Rust 已封装**：`commands/mihomo.rs` 已有 `get_mihomo_connections()`、`close_mihomo_connection(id)`、`close_all_mihomo_connections()`（`mihomo.rs:294/307/316`）。
4. **连接元数据足够富**：`TrackerInfo` 有 `id`(uuid)、`metadata`（含 `host`/`sniffHost`/`process`/`processPath`/`rule`/`rulePayload`/`destinationIP`/`sourceIP`/`dnsMode`/`remoteDestination` 等）、`upload`、`download`、`start`、`chains`、`providerChains`。

### 4.2 技术方案

**新增一层"条件匹配器"**：Rust GET snapshot → 按谓词过滤 → 对命中 id 逐个 DELETE。mihomo 缺条件杀，条件逻辑放 Rust 侧即可，**无需改 mihomo**。

```
前端"一键杀"按钮 / Rust 侧死链清理
        │
        ▼
core/connections.rs（新建）：ConnectionFilter 谓词
        │  匹配维度（全部来自 TrackerInfo.metadata）：
        │    · host / sniffHost（域名）           · process / processPath（进程）
        │    · rule / rulePayload（命中规则）      · destinationIP / sourceIP
        │    · chains / providerChains（链路/机场） · dnsMode / remoteDestination
        ▼
GET /connections → 过滤 → 逐个 DELETE /connections/{id}（限流，防一次全杀风暴）
```

**两个使用场景**：

1. **用户"强制断开"按钮**（前端驱动）：选中某节点/某域名/某进程 → 构造 `ConnectionFilter` → `kill_mihomo_connections(filter)`。前端 `services/connections.ts` + `stores/connections.ts` 已有数据通路，只需加一个带过滤参数的 kill 命令。
2. **Rust 侧死链自动清理**（后端驱动）：当节点延迟测速异常（`GET /proxies/{name}/delay` 超时/超阈值）时，supervisor 或一个后台任务自动构造 `ConnectionFilter{chains 包含该节点}` → 清理挂在该节点上的存量连接，逼它们重路由到健康节点。**这正好与方向①的 Layer C 衔接**。

### 4.3 涉及 Rust 模块

| 模块 | 改动 |
|---|---|
| `core/connections.rs` | **新建**：`ConnectionFilter` 结构 + `filter(conns) -> Vec<id>` + `kill_by_filter`（含限流） |
| `commands/mihomo.rs` | 新增 `kill_mihomo_connections(filter)` 命令（GET → filter → 逐个 DELETE）；`get_mihomo_connections` 从返回 `String` 升级为强类型 `Snapshot`（`serde_json` 零容忍） |
| `core/supervisor.rs` | 挂接"节点延迟异常 → 清理存量连接"的后台任务（可选，二期） |
| `services/connections.ts`、`stores/connections.ts` | 新增"按条件断开"的动作 + 前端按钮 |

## 5. 横向议题：状态机收敛与前端防抖（贯穿方向二/三）

三个方向会共同触碰一个根问题：**当前 `KernelState` 的写入点分散**（`start()`/`stop()`/drain task 三处），且前端对事件是"来一条渲一条"，没有滞回。建议：

1. **引入单一状态机**：`KernelState` 扩展暂态（如 `Recovering`），所有转换经 supervisor 一个入口。
2. **事件合并 + 滞回**：后端把高频翻转合并成稳定态再推；前端对连续翻转做 debounce，避免 `starting↔crashed` 导致的 store 抖动风暴。
3. **崩溃"死因"结构化**：`TerminatedPayload{code,signal}` 目前只进了 JSON 事件，建议映射成可读 cause（端口占用/配置错误/被 kill），供 UI 与日志直接展示。

## 7. 风险与回滚

- **方向二下沉的竞态风险**：自动重启与用户手动 start/stop 可能打架 → 用单一 supervisor 状态机 + `Recovering` 暂态收敛，用户手动操作时先"取消"在途自动重启。
- **方向三全杀风暴**：条件命中过多时逐个 DELETE 可能瞬间打爆 controller → 加**限流**（如每 50ms 一条）+ 单次上限（如 100 条），超出则分批。
- **方向一过度解析风险**：mihomo 文本格式随版本变化 → Layer B 必须"命中则抽、未命中则整行透传"，绝不让新版本日志把 ingest 打崩（维持现有 `Option`-gated 零 panic 约定）。
- **回滚**：三个方向相互解耦，可独立 revert；Step 1 若竞态处理不当，可退回"前端退避"方案（保留 commit 历史）。

## 附：侦察到的最关键三条"拨乱反正"

1. **方向①的原始目标在日志侧不可实现**——mihomo `?format=structured` 的 `Fields` 是空数组，细粒度信号必须改从 `/connections` metadata + `/dns/query` 计时采集。
2. **后端其实从不自动重启**——`sidecar.rs` 崩溃只 `break`，自动重启一直偷偷靠前端 `kernel.ts::autoRestartOnCrash`，窗口一关就失效。这是本次"大手术"最该补的洞。
3. **`DELETE /connections` 的能力其实早就封装好了**——缺的只是 Rust 侧一层条件匹配，mihomo 本身不用改。
